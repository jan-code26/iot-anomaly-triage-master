The Problem

One alarm threshold for every engine,
everywhere — that's the problem

A jet engine cruising at 35,000 ft behaves very differently from one at sea level. Treating both the same is like flagging a car for going "too slow" on a highway because the speed camera was calibrated for a school zone.

Why monitoring fails today

Imagine setting a speed camera to flag any car going under 60 mph — on both a highway and a school zone. The camera would alert constantly in the school zone, even though 30 mph is perfectly legal there.

Aircraft engine monitors do the same thing. They compare every reading to an average across all flight conditions. A fan spinning at the correct speed for 35,000 ft looks dangerously slow compared to the sea-level average. The alarm fires. Nothing is wrong.

The fix is to ask a different question. Not "is this reading normal on average?" but "is this reading normal for where this engine is right now?"

The Solution

Regime-aware causal scoring,
physics-verified

Anomaly scoring is conditioned on the current operating regime — not evaluated against a global baseline. A physics veto then distinguishes sensor faults from real engine degradation.

1

Regime Classification

First, figure out what kind of flight this engine is on.

KMeans assigns each incoming reading to one of 6 flight-condition clusters based on altitude, Mach number, and throttle angle.

scikit-learn KMeans
2

Causal Scoring

Then compare it only to similar flights — not the whole fleet.

Per-cluster regression models predict what each sensor should read for this flight condition. The anomaly score is how far off the reading is from that prediction — not from a global average.

DoWhy DAG · sklearn
3

Physics Veto

Double-check: broken sensor, or real engine problem?

A statistical test checks whether two pressure sensors still move together the way physics demands. If they stop tracking each other, a sensor has failed — not the engine. This prevents false degradation alerts from sensor noise.

G-test · χ²=26.30
4

LLM Explanation

Finally, write a plain-English note for the engineer on duty.

An AI language model (Llama-3) reads the scores and physics result, then writes a one-sentence explanation the maintenance crew can act on — not just a raw number.

LangGraph · Groq
Causal DAG

op_setting_1 (Altitude) → AirDensity → CoolingEfficiency → sensor_4
op_setting_2 (Mach) → TipSpeed → HPCLoading → sensor_11, sensor_15
op_setting_3 (TRA) → FuelFlow → CombustorTemp → sensor_3, sensor_9

Causal DAG: flight conditions drive expected sensor values through known physics. Anomaly scores measure the gap between what was read and what physics predicted — not against a global average.

The retrained baseline experiment

To rule out domain-shift correction as the mechanism, we tested a retrained z-score variant that recomputes per-sensor means and standard deviations from FD002 and FD004 training data respectively. Both retrained variants still produce 100% false positive rates (F1 = 0.000, Wilcoxon p = 0.548 on FD002, p = 0.751 on FD004 — statistically indistinguishable from the global z-score). The pooled mean of a multi-condition dataset sits in the middle of the regime space: a healthy high-altitude engine still deviates substantially from the pooled mean. Retraining cannot fix this. Regime conditioning can.

System Architecture

A seven-node LangGraph agent with operator feedback

Every reading above threshold triggers a stateful multi-step agent. Each node writes a reasoning trace to PostgreSQL — operators can correct decisions and the system learns from feedback.

DETECTION
50/50 blend of global z-score (recall) and causal score (precision). Threshold 0.3 for UNCERTAIN, 0.6 for ALERT.
PHYSICS VETO
G-test on 5×5 contingency table of HPC temp/pressure (χ²=26.30, df=16). Halves score if coupling broken — sensor fault, not degradation.
FEEDBACK LOOP
Operators label alerts TRUE_POSITIVE / FALSE_POSITIVE / UNCERTAIN. 2+ false positive labels on an engine → 0.7× confidence penalty on future alerts.
